Le backend tourne dans Docker Desktop sur ton PC (theme1-dev-backend-1), et le port 4000 est ouvert sur le PC lui-même. Il faut donc l'IP Wi-Fi de ton PC : 10.139.91.177.

N'utilise pas les autres adresses que montre ta machine :

172.19.80.1 et 172.27.80.1 sont des réseaux virtuels internes à Windows (WSL et Hyper-V), qu'un téléphone ne peut pas joindre.
Les adresses en 169.254.x.x ne sont pas utilisables non plus.

Trois conditions pour que ça marche :

Même Wi-Fi : le téléphone doit être sur le même réseau que le PC.
Pare-feu Windows : il doit laisser passer le port 4000 en entrant.
Réseau partagé : une adresse en 10.139.x.x ressemble à un réseau d'école ou d'entreprise. Ces réseaux bloquent souvent les échanges directs entre appareils. Dans ce cas, utilise le partage de connexion du téléphone pour le PC, ou un tunnel comme ngrok ou cloudflared.
Autre point : cette IP change quand tu changes de réseau, et il faudra alors refaire le build.

Si le backend tourne sur une VM distante
Si tu parles de ta VM (par exemple le déploiement Oracle mentionné dans auth_controller.ex), mets son IP publique à la place. Ça marche alors depuis n'importe quel réseau, sans contrainte de Wi-Fi ni de pare-feu local. Il faut quand même que le port 4000, ou le port exposé, soit ouvert dans les règles réseau de la VM.

Au démarrage de l'app :

Session sur le téléphone ?
Si non, écran de connexion (réseau obligatoire).
Si oui, déverrouillage par empreinte ou code. En cas d'annulation, l'écran de connexion propose « Unlock with fingerprint or PIN ».
En ligne :
la session est vérifiée auprès du serveur, et le JWT est renouvelé automatiquement s'il a expiré ;
un 401 ramène à l'écran de connexion, avec la raison affichée.
Hors ligne : l'app s'ouvre avec le profil enregistré, si la dernière vérification date de moins de 7 jours. Sinon, un message demande de se reconnecter.
Pendant l'utilisation :

JWT expiré (401) : l'app fait un refresh, puis rejoue la requête une fois, sans que l'utilisateur le voie.
Retour à la connexion : si la session expire en arrière-plan (par exemple pendant la synchro), l'app ramène à l'écran de connexion. L'outbox est conservée pour ce même utilisateur.
Autre utilisateur sur le téléphone : le cache du précédent est effacé. Ses actions en attente restent séparées.
Choix et limites à connaître
Téléphone sans verrouillage d'écran : le Keystore refuse de fonctionner. Les tokens restent alors en mémoire seulement, et il faut se reconnecter à chaque lancement. Je n'utilise jamais de stockage non chiffré en repli.
Empreinte non configurée : le Keystore exige déjà un téléphone verrouillé, donc la session s'ouvre sans demande.
Déconnexion hors ligne : le token est supprimé du téléphone, mais il ne peut pas être révoqué côté serveur. Il expire seul au bout de 7 jours au maximum.
Après la mise à jour : les anciens tokens mobiles, valables 24 h et non chiffrés, sont effacés. Il faudra se reconnecter une fois.
À tester sur l'émulateur
npm run android, puis se connecter.
Fermer et rouvrir l'app : l'empreinte doit être demandée. Sur l'émulateur, on la simule avec Extended controls → Fingerprint.
Passer en mode avion, rouvrir l'app, puis pointer.
Remettre le réseau : le pointage part. Le JWT a pu expirer entre-temps : c'est le refresh qui doit prendre le relais.
Changer le mot de passe depuis le web : au prochain appel, le téléphone doit revenir à l'écran de connexion.
